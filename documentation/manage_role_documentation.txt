================================================================================
STOCKDO: MANAGE ROLE (CONTROL PANEL) EXHAUSTIVE DOCUMENTATION
================================================================================

This document outlines the Manage Role module, located within the Control Panel. 
Role Management is the beating heart of StockDo's Role-Based Access Control (RBAC) 
architecture. It dictates precisely which modules and actions (View, Add, Edit, Delete, Print) 
any given user can perform.

--------------------------------------------------------------------------------
1. ARCHITECTURAL OVERVIEW
--------------------------------------------------------------------------------
The Role model stores its permissions as a JSON/Array payload. The ERP recognizes 
23 distinct functional modules (e.g., "Master Data", "Challan", "Billing", "Daybook", 
"Local Sale"). 

Instead of hardcoding roles like "Admin" or "Staff", StockDo allows the creation 
of infinitely flexible custom roles. A role acts as a security profile that is 
then assigned to a `User`. The entire frontend application is wrapped in a 
`usePermissions()` hook that queries these exact role settings to dynamically 
hide or render UI elements (like the "Add New" button in Materials).

--------------------------------------------------------------------------------
2. FRONTEND CONTROLLER & INTERFACE
--------------------------------------------------------------------------------
* Page Location: `frontend/src/app/dashboard/control-panel/roles/page.tsx`

The interface adopts a distinct, specialized Dark Mode UI (`bg-[#020817]`) to 
visually distinguish the Control Panel from standard operational CRMs.

--- UI LIFE-CYCLE ---
1. Hybrid Data Entry (Inline Creation + Modal Editing):
   - Inline Creation: To create a new role, the user types a name into the permanent 
     "Add New Row" at the bottom of the table. By default, new roles are generated 
     with a null scope (all 23 modules locked).
   - Modal Editing: Clicking "Edit" opens a massive `max-w-5xl` Dialog containing 
     the Granular Security Matrix.

2. The Granular Security Matrix (The Matrix Grid):
   The matrix maps all 23 modules down the Y-axis and 6 action columns across 
   the X-axis:
   - `view` (Read access to the page)
   - `add` (Create access)
   - `edit` (Update access)
   - `delete` (Destroy access)
   - `print` (Export access)
   - `fullControl` (Internal Access Toggle)
   
   Checking `fullControl` automatically cascades and checks all other boxes for 
   that specific module via the `handlePermissionChange` handler.

3. Live Session Updates:
   A critical feature of the `handleSave` function is that if the logged-in administrator 
   is editing *their own* role, the frontend immediately patches the global `useAuthStore` 
   session. This prevents the user from having to log out and log back in to see 
   newly granted permissions.

--------------------------------------------------------------------------------
3. BACKEND SERVICE & PERMISSIONS SCHEMA
--------------------------------------------------------------------------------
* API Router: `backend/src/roles/roles.controller.ts`
* Service logic: `backend/src/roles/roles.service.ts`

--- API BEHAVIOR ---
- `POST /roles`: Accepts a `name` string and a highly structured `permissions` JSON array.
- `GET /roles`: Returns all roles. Crucially, it uses Prisma `_count: { select: { users: true } }` 
  to tell the frontend how many active users are currently assigned to this security profile.
- `DELETE /roles/:id`: Removes the role. Note: A role cannot be deleted if users 
  are currently assigned to it (enforced by DB foreign-key constraints).
